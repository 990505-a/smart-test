# 大系统测试（游戏玩法用例设计）

## 概述

大系统（多阶段大型玩法）测试用例 = **固定九段骨架 × 阶段时间轴 × 边界交叉枚举**。

三条核心原则：

1. **骨架固定**：无论什么玩法，顶层永远是同一套九段结构（见下），评审时先查骨架完整性再查细节。
2. **沿状态机展开**：主流程按活动阶段（报名→预选→匹配→正赛→结算→展示→休赛/新赛季）推进，每个阶段都拆「阶段开始前 / 进行中 / 结束期」三个观察点。
3. **用例是树不是表**：条件→操作→预期 逐层嵌套，叶子打执行标记（√ 通过 / X 失败 / 空 未执行）。条件层枚举边界，预期层落到"与配置一致"或具体表现。

---

## 九段骨架（顶层目录模板）

```
<系统名>
├── 1. 前置准备          — wiki 需求/设计文档链接、配置表清单（表名+用途）、
│                          GM 指令清单（跳阶段/加机器人/重开战斗/开合服）、
│                          测试环境（多服、多账号、多宗门、分辨率）
├── 2. 入口检查          — 解锁条件边界矩阵、入口位置、入口状态随阶段变化、各阶段拍脸/弹窗
├── 3. 活动主流程        — 按阶段时间轴展开（见下方主流程模板）
├── 4. 红点相关          — 每个红点三件套：出现规则 / 消失规则 / 红点路径（逐级到按钮）
├── 5. 配置检查          — 全部相关配置表逐表核对，数值类用例统一挂"与配置一致"
├── 6. 日志相关          — 每个日志：日志名 + 触发条件 + 打印数据与实际一致
├── 7. 协议相关          — 每条协议：cmd + 用例（传参/时序/资格，见协议模板）
├── 8. 异常测试          — 重启服务器、重启客户端/切后台、重开战斗、强开强关活动、
│                          并发/连点器、数据落地与恢复
└── 9. 专项测试          — 按需：分辨率适配、合服、压测、跨服互通
```

规则：骨架段不可省略；某段确不适用时保留标题并写"不适用原因"，防止评审时争议是遗漏还是裁剪。

---

## 第 2 段：入口检查模板

- **解锁边界矩阵**：把所有解锁条件做笛卡尔积——等级(恰等于 / 高于 / 低于) × 前置系统(有/无，如未加入宗门) × 服务器状态(已飞升/未飞升、匹配期前/后) × 时间(进入报名期前/后)。每个组合一条"入口解锁/不解锁"用例。等级升级跨过解锁线的瞬间也要测（14→15 状态实时刷新）。
- **入口位置**：枚举所有入口逐条验证（主界面、右侧活动列表、问剑盟/宗门页签、快捷入口…），不要写"各入口正常"一条带过。
- **入口状态**：入口文案/倒计时随每个活动阶段变化（报名中、X小时后预赛、竞猜进行中、128进64…对决结束）。对决结束次日早 8 点入口消失这类"消失时点"要单列。
- **拍脸/弹窗**：每个阶段的登录弹窗——信息加载正确、跳转正确、关闭正常、只弹一次、勾选"不再提醒"后重启客户端生效。

## 第 3 段：活动主流程模板

按阶段时间轴组织，每个阶段内套用功能块清单（按玩法取用）：

**阶段骨架**
```
<阶段名>（写明确切时间窗，如 周日19:00-20:00）
├── 开始前   — 入口/主界面显示倒计时；倒计时格式降级：N天→不足1天显N小时→不足1小时显N分
├── 进行中   — 状态刷新、参与操作、数据实时变化（人数+1、积分、榜单）
└── 结束期   — 满足条件→进入下一阶段；不满足条件→回退/关闭/顺延，两种都要测
```

**功能块清单**（大系统常见，缺哪个补哪个）

| 功能块 | 必测点 |
|---|---|
| 匹配规则 | 奇偶数（落单者轮空/镜像）、首尾匹配、同胜场分组、轮空顺延（第一已轮空→顺延第二）、跨组不匹配、档位分界（128/256/512/1024、16/32/48）、镜像数据只算本人战绩 |
| 排名/结算 | 多级 tiebreaker 逐级枚举：胜场数→首败轮次→总战力→上榜时间→随机，每级写 A/B 对比用例并测"上层相同才看下层" |
| 名单/数据锁定 | 锁定时点、锁定后养成/战力变化不影响匹配、多组织报名最后归属去留、锁定期组织成员进出限制 |
| 次数/资格 | 每日/每周定时发放（8:00）、发放上限、消耗后不重复发、重登不补发、周重置不累计、跨玩法共享上限 |
| 奖励 | 见下方"奖励四问" |
| 抽奖/奖池 | 概率与配置一致、同概率按权重、个人保底/全服(宗门)保底、提前出货保底重置、限量物品抽取完停止保底、换组织后保底/限量是否延续、周一 8:00 重置 |
| 竞猜/投注 | 投注上下限（50-500 这类边界）、重复投注拦截、余额不足、赔率随人数实时变化、倍率取投注时点值、结算三态：猜中（返奖）/未中（不返还）/无结果（全额返还） |
| 商店/兑换 | 限购次数、货币不足拦截、层数解锁消耗、并发兑换同道具不超上限、赛季刷新重置限购与层数、有境界/种族区分的道具发错端要拦截 |
| 礼包/付费 | 免费限领、拉起订单未支付占次数、超限购客户端灰+服务端拦、并发购买只弹一次、活动结束无法拉起 |
| 组队 | 创建/加入/退出/踢人/解散、队长转移限制、与其他玩法队伍互斥、分享链接（满员不可入、跨队跳转踢出原队）、本服/跨服频道分享范围 |
| 战斗 | 通用战斗 checklist + 玩法专属机制（见下） |
| 战令/任务 | 任务类型逐条可完成、进度条、跳转前往、经验与配置一致、付费档购买前后进度表现 |

**通用战斗 checklist**（组队/PVP 玩法直接复用）
对象类型（boss/据点/本服玩家/非本服玩家×挂机/非挂机）、法宝、神通、领域、法相、灵兽、符箓、回血/回蓝道具、操作模式（手动/自动/锁定）、其他系统加成属性在战斗场景内的正确性、死亡复活（buff 保留/重置）、地图传送、战斗时长限制与超时判定（剩余血量百分比定胜负）、切出战斗的快捷入口、战斗结算界面分态（助战/非助战 × 击杀/未击杀 × 有/无进度节点）。

**客户端/UI**（主流程末尾单列）
界面分区描述（上/中/下）、逐按钮点击验证（跳转/弹窗）、页签切换、页面停留时阶段自然过渡（状态与数据刷新）、子页面逐个（记录/奖励/商店/排名/战况）。

**特殊情况**（每个大系统必有的散点）
活动进行中删号/删角色、匹配后数据变化、轮次中途服务器重启（可重打当轮）、观战回放中重启客户端、结算前后切换/退出/被踢组织、24:00 前几秒的临界操作（释放/进入副本照常结算）、与其他活动同档期的互斥或独立结算。

## 奖励四问（每类奖励必答）

1. **给谁**：领取资格矩阵——结算前在组织 / 结算后加入 / 结算前退出又重进 / 被踢 → 分别可领、不可领、还是补发。
2. **给什么**：类型、数量、档位"与配置一致"；0 胜/未参与是否仍有参与奖。
3. **怎么给**：正常到账；**背包满 → 邮件补发**。
4. **没领怎么办**：展示期/下一轮/赛季结束的**未领取邮件补发**时点；补发后不重复出现领奖按钮；跨轮不重复补发。

## 协议用例模板（第 7 段）

```
<协议名>
├── cmd：GameServer:send("<op>", <args>)   （附参数类型，如 (string) system）
└── 用例
    ├── 传参：类型传错 / 不传 / 非法值 / 超 int32
    ├── 时序：非活动阶段发、活动结束后发
    ├── 幂等：已领取/已购买后重发 → 服务端校验拦截
    └── 资格：未参与/不在对应组织/未解锁发 → 校验失败
```
预期统一写"服务端校验正常，领取/购买失败"，不只写"报错"。

## 红点三件套（第 4 段）

每个红点独立成组：**出现规则**（精确条件，如"自身有未消耗的开奖次数"）→ **消失规则**（进入页面/完成操作/阶段结束，注意"点击不操作红点仍在"这类细分）→ **红点路径**（从主界面页签→功能入口→按钮逐级列出）。末尾加一条"未参与/未解锁玩家红点表现"和"所有红点实时刷新"。

## 异常与数据（第 8 段）

- 重启服务器：分类数据逐项确认不变（匹配、报名、名单、竞猜、排行、领奖标记、限购次数、解锁层数）。
- 重启客户端/切后台：展示数据不变、倒计时恢复。
- 重开战斗：新数据覆盖旧数据、已竞猜结果不变、可重新竞猜、奖励可领。
- 强开/强关活动：改配置表使开启时间早于/晚于计划表，验证开与关。
- 并发/连点：抽取、购买、兑换的并发不超上限。
- 数据落地：强制关服验证写盘。

## 交付（Markdown 草稿 + 工作流门禁 + 飞书导图）

本技能产出的用例树**原样保存为 Markdown 草稿**，不做压扁：按九段骨架建顶层分组、功能块/子功能逐层建子分组；用例挂在最末级分组上；「条件→操作→预期」嵌套树直接使用现有 Markdown steps 语法。每个可识别用例标题下增加独立元数据注释：

```markdown
<!-- CASE: CASE-MODULE-001; REQ: REQ-MODULE-001; RISK: RISK-MODULE-001 -->
```

`CASE` 必须唯一，`REQ`/`RISK` 至少一个且可多值；不要把 ID 写进标题、步骤或可见表格，以免污染飞书节点。通过 `save_case_document` 保存完整文档，保存后必须运行确定性 `lint_case_document`；Lint 通过后再运行 `review_case_document`。只有人工批准的版本才可发布，飞书导出只是同步展示，不等同于批准或内部发布。

## 编写风格规则

- 用例树：条件→操作→预期，一层只表达一个变量；叶子才是结果（√/X/空）。
- 一切数值写"与配置一致"并注明配置表字段，禁止写死期望值（除非需求明确定死）。
- 边界五件套：**恰好等于、差一点、超一点、空/零、最大值**；奇偶成对；时间边界测"前几秒"。
- 多实体命名用 A/B/C 玩家 + 1/2 宗门（服务器），交叉矩阵展开（A 在 A 宗报名后转 B 宗、C 同时在 A/B 报名…）。
- GM 指令写进前置准备（偏移到各阶段、加机器人、重开正赛），方便复现长周期活动。
- 服务端排查用例附查询指令（如 RankD.get_rank_list(...)、ActivityServerMatchGameD.query_entire_dbase()）。

## 完成前自检

- [ ] 九段骨架齐全，无一段为空且未说明原因
- [ ] 每个阶段都有 前/中/后 三个观察点，倒计时格式降级已测
- [ ] 解锁条件全组合矩阵已展开，升级跨线瞬间已测
- [ ] 排名 tiebreaker 每一级都有 A/B 对比用例
- [ ] 奖励四问全部有答案（资格矩阵、背满邮件、未领补发）
- [ ] 红点全部三件套 + 路径逐级
- [ ] 协议至少覆盖：传参错、非阶段、重复发、无资格
- [ ] 重启服务器/客户端、重开战斗、并发、强开关活动已列
- [ ] 所有数值挂"与配置一致"，配置表逐表登记
- [ ] 日志逐条登记触发条件
- [ ] 临界时间点（8:00 / 24:00 / 周一刷新 / 活动结束前几秒）有用例

## 常见错误

| 错误 | 纠正 |
|---|---|
| 用例写成"功能正常"一句话 | 拆成条件树，预期落到具体表现或配置 |
| 只测"满足条件"路径 | 每个条件必配不满足分支；每个数值配上/下边界 |
| 奖励只测正常领取 | 四问：资格矩阵、配置一致、背满邮件、未领补发 |
| 只测客户端拦截 | 服务端协议校验单独成组（改包/重发/无资格） |
| 忘掉"切换/退出/被踢组织" | 活动周期内身份变化是最高频漏测点 |
| 忘掉跨玩法交互 | 同档期活动互斥/独立结算、共享次数上限 |
| 时间相关只改一次表 | 周一 8:00、每日 8:00、24:00、活动前几秒都要单独推进验证 |

## 不适用

单个小功能、纯 UI 调整、纯数值改动——直接写常规功能用例即可，套此骨架是浪费。判断标准：无多阶段时间轴、无跨系统交互、无周期重置，就不算"大系统"。
