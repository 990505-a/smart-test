# 测试策略制定 Skill

## 激活场景
- 需求分析完成后，开始制定整体测试方案
- 用户询问"应该测哪些方面？"
- 用户需要评估测试覆盖是否充分
- 项目有时间约束，需要优先级排序

---

## KUFI 四象限分类（D-04）

基于需求分析结果，将所有功能点按 KUFI 四象限进行分类，确定测试深度和资源分配策略。

### K - Know（已知领域）

**定义**：团队熟悉的功能特性，有丰富的测试经验和成熟的方法论。

| 维度 | 说明 |
|------|------|
| 特征 | 标准CRUD、常规表单验证、通用登录注册等 |
| 测试深度 | 标准功能测试，低测试深度 |
| 用例密度 | 低（每个功能点 2-4 条用例） |
| 设计方法 | 等价类划分 + 基本边界值 |
| 资源分配 | 低优先级投入，可考虑自动化覆盖 |
| 示例 | 用户名密码登录、手机号注册、个人信息修改 |

### U - Understand（理解领域）

**定义**：功能有一定复杂性，需要深入理解业务逻辑，但领域知识可获取。

| 维度 | 说明 |
|------|------|
| 特征 | 多条件业务规则、复杂计算逻辑、跨模块联动 |
| 测试深度 | 增强测试，中等测试深度 |
| 用例密度 | 中（每个功能点 4-8 条用例） |
| 设计方法 | 等价类 + 边界值 + 决策表 + 场景法 |
| 资源分配 | 标准投入，关键路径需手工验证 |
| 示例 | 优惠券叠加规则、多级审批流程、跨系统数据同步 |

### F - Familiar（熟悉风险领域）

**定义**：功能存在已知风险模式，历史上有较多缺陷，需要重点关注。

| 维度 | 说明 |
|------|------|
| 特征 | 并发操作、事务处理、状态机、安全相关 |
| 测试深度 | 深度测试，高测试深度 |
| 用例密度 | 高（每个功能点 8-15 条用例） |
| 设计方法 | 状态转换 + 场景法 + 错误推测 + 安全测试 |
| 资源分配 | 高优先级投入，必须手工+自动化双重覆盖 |
| 示例 | 库存扣减并发、支付状态机、权限越权检查 |

### I - Infer（推断未知领域）

**定义**：全新功能或高度不确定的特性，缺乏历史参考，需要探索性测试。

| 维度 | 说明 |
|------|------|
| 特征 | 全新业务模式、技术栈升级、第三方集成 |
| 测试深度 | 探索性测试，最大测试深度 |
| 用例密度 | 最高（每个功能点 15+ 条用例 + 探索性测试会话） |
| 设计方法 | 场景法 + 错误推测 + 探索性测试 + Pairwise |
| 资源分配 | 最大投入，必须资深测试人员参与 |
| 示例 | AI推荐算法、新支付渠道接入、跨平台数据迁移 |

### KUFI 分类决策流程

```
对每个功能点执行：
Step 1: 是否为团队首次接触的功能类型？
  ├─ 是 → I（Infer）
  └─ 否 → 继续

Step 2: 功能是否涉及已知风险模式（并发/安全/事务）？
  ├─ 是 → F（Familiar）
  └─ 否 → 继续

Step 3: 功能是否有复杂业务规则（多条件/跨模块/状态机）？
  ├─ 是 → U（Understand）
  └─ 否 → K（Know）

特殊规则：
- 所有涉及金钱/支付的功能至少为 U 级
- 所有涉及用户隐私的功能至少为 F 级
- 所有 P0 优先级功能至少为 U 级
```

### KUFI 与测试资源分配矩阵

| KUFI等级 | 功能占比参考 | 用例占比参考 | 自动化率 | 探索性测试 |
|----------|------------|------------|---------|-----------|
| K（已知） | 40-50% | 20-25% | 80%+ | 不需要 |
| U（理解） | 25-35% | 30-35% | 50-70% | 可选 |
| F（熟悉风险） | 15-20% | 25-30% | 60-80% | 建议 |
| I（推断未知） | 5-10% | 15-20% | 30-50% | 必须 |

## 测试类型选择决策树

### 功能测试（必选）
**适用条件**：所有功能性需求
```
正向流程测试   -> 验证核心业务路径（Happy Path）
逆向流程测试   -> 验证错误处理与异常场景
边界条件测试   -> 验证输入边界处理
等价类测试     -> 验证数据分类处理
```

### 接口测试（API项目必选）
**适用条件**：存在HTTP API、RPC、消息队列
```
契约验证       -> 请求/响应格式符合接口文档
状态码验证     -> HTTP状态码语义正确
认证鉴权       -> Token/Session/OAuth验证
幂等性验证     -> 重复请求处理
```

### 安全测试（涉及用户数据必选）
**适用条件**：认证、授权、用户数据、支付
```
SQL注入测试    -> 数据库查询注入防护
XSS测试        -> 跨站脚本防护
CSRF测试       -> 跨站请求伪造防护
越权测试       -> 水平/垂直越权验证
敏感数据保护   -> 密码、身份证、手机号脱敏
```

### 性能测试（高并发场景必选）
**适用条件**：用户量>1000、高频接口、数据密集型操作
```
基准性能测试   -> 单用户响应时间基线
负载测试       -> 预期并发用户数下的表现
压力测试       -> 极限并发用户数
稳定性测试     -> 7x24小时长时间运行
```

### 兼容性测试（多端产品选择）
**适用条件**：Web端、移动端、多浏览器
```
浏览器兼容     -> Chrome/Firefox/Safari/Edge
设备兼容       -> iOS/Android 多机型
分辨率适配     -> 375px/768px/1024px/1920px
OS版本兼容     -> iOS 14+/Android 8+
```

### 可用性测试（ToC产品选择）
**适用条件**：面向终端用户的消费级产品
```
交互逻辑验证   -> 操作反馈是否即时
错误提示质量   -> 错误信息是否清晰可操作
无障碍验证     -> WCAG 2.1 AA级标准
```

## 优先级策略矩阵

基于**业务影响 x 风险概率**进行优先级评定：

```
              | 低概率 | 高概率
高业务影响    |   P1   |   P0
低业务影响    |   P3   |   P2
```

### 优先级定义（强制遵循）
| 级别 | 名称 | 执行时机 | 通过率要求 | 典型场景 |
|------|------|---------|-----------|---------|
| **P0** | 阻塞级 | 每次构建/发布前 | 100% | 核心支付流程、用户登录 |
| **P1** | 高优先级 | 每个Sprint结束 | >=95% | 主要业务功能、数据准确性 |
| **P2** | 中优先级 | 版本发布前 | >=90% | 辅助功能、优化项 |
| **P3** | 低优先级 | 有时间则执行 | 尽力覆盖 | 边缘场景、UI细节 |

## 特殊策略场景

### 时间紧迫时的策略（冒烟测试套件）
> 当发布时间压缩时，快速构建最小有效测试集：
> 1. 只执行P0级用例（核心流程不超过20个用例）
> 2. 覆盖所有主要功能的正向流程
> 3. 覆盖最高风险的异常场景（支付失败、数据丢失）

### 新功能 vs 存量功能策略
- **新功能**：全面覆盖，包含边界和异常（设计深度=深）
- **存量功能**（受新功能影响）：聚焦影响区域（设计深度=中）
- **存量功能**（未受影响）：仅冒烟验证（设计深度=浅）

## 测试类型选择的量化评分卡

企业级测试策略不能仅凭经验判断，需要对每个测试类型进行量化评估。

### 评分维度与权重

| 评分维度 | 权重 | 评估标准 |
|---------|------|---------|
| 业务风险 | 30% | 该功能失败的业务影响程度（1-5分） |
| 技术风险 | 25% | 技术复杂度、变更频率、历史缺陷密度（1-5分） |
| 合规要求 | 20% | 行业法规是否强制要求（1-5分） |
| 用户影响 | 15% | 影响用户数量和使用频率（1-5分） |
| 成本效益 | 10% | 测试投入与预期收益的匹配度（1-5分） |

### 测试类型执行决策

对每个测试类型，计算加权总分：

```
总分 = 业务风险*0.3 + 技术风险*0.25 + 合规要求*0.2 + 用户影响*0.15 + 成本效益*0.1
```

| 总分范围 | 决策 | 说明 |
|---------|------|------|
| 4.0-5.0 | **必须执行** | 核心测试类型，投入最大资源 |
| 3.0-3.9 | **建议执行** | 重要测试类型，标准资源投入 |
| 2.0-2.9 | **有条件执行** | 视时间和资源情况决定 |
| 1.0-1.9 | **可选执行** | 仅在有富余资源时考虑 |
| <1.0 | **不执行** | 当前版本暂不覆盖 |

### 评分示例

**场景**：电商订单支付模块

| 测试类型 | 业务风险 | 技术风险 | 合规要求 | 用户影响 | 成本效益 | 加权总分 | 决策 |
|---------|---------|---------|---------|---------|---------|---------|------|
| 功能测试 | 5 | 4 | 3 | 5 | 5 | 4.45 | 必须执行 |
| 接口测试 | 4 | 5 | 3 | 3 | 4 | 3.95 | 建议执行 |
| 安全测试 | 5 | 4 | 5 | 4 | 3 | 4.30 | 必须执行 |
| 性能测试 | 3 | 3 | 2 | 4 | 3 | 3.00 | 有条件执行 |
| 兼容测试 | 2 | 2 | 1 | 3 | 2 | 1.95 | 可选执行 |

## 测试环境策略

### 环境拓扑规划

```
[开发环境] -> [测试环境] -> [预发布环境] -> [生产环境]
     ^            ^              ^
   单元测试    集成测试      验收测试
   接口测试    系统测试      回归测试
   冒烟测试    性能测试
               安全测试
```

### 环境配置要求

| 环境 | 用途 | 数据要求 | 配置要求 |
|------|------|---------|---------|
| 测试环境 | 功能/接口/安全测试 | 合成测试数据（不可使用生产数据） | 与生产环境架构一致，资源配置可降级 |
| 性能环境 | 性能/压力/稳定性测试 | 与生产等比例数据量 | 与生产环境资源配置一致或按比例缩放 |
| 预发布环境 | 回归测试/UAT验收 | 生产数据脱敏副本 | 与生产环境完全一致 |

### 数据准备策略

| 数据类型 | 来源 | 注意事项 |
|---------|------|---------|
| 基础数据 | 手工构造 + 脚本生成 | 覆盖所有业务场景所需的基准数据 |
| 边界数据 | 基于字段约束构造 | 覆盖 min-1, min, max, max+1 |
| 性能数据 | 批量生成脚本 | 数据量需达到性能测试目标量级 |
| 安全数据 | 标准Payload库 + 定制 | 确保Payload符合实际攻击场景 |
| **严禁使用生产数据** | - | 违反个保法/GDPR，必须使用脱敏或合成数据 |

## 自动化测试策略

### 自动化适用性评估

对每个功能模块，评估是否适合自动化：

| 评估维度 | 适合自动化 | 不适合自动化 |
|---------|-----------|------------|
| 执行频率 | 每次构建都执行 | 偶尔执行 |
| 稳定性 | 功能稳定，UI/接口不常变 | 频繁变更，尚未稳定 |
| 复杂度 | 步骤明确，判定标准清晰 | 依赖主观判断、探索性测试 |
| 执行成本 | 手工执行耗时 > 自动化维护成本 | 手工执行耗时 < 自动化维护成本 |
| 回归价值 | 高价值回归场景 | 一次性验证场景 |

### 自动化分层策略（测试金字塔）

```
         /\
        /  \     E2E 端到端测试（10%）
       /    \    -> 核心业务流程验证
      /------\
     /        \   接口/服务测试（30%）
    /          \  -> API契约、业务逻辑验证
   /------------\
  /              \ 单元测试（60%）
 /                \ -> 函数/方法级验证
/__________________\
```

**企业级目标**：
- 单元测试覆盖率 >= 80%
- 接口测试覆盖所有外部接口
- E2E 测试覆盖所有 P0 业务流程
