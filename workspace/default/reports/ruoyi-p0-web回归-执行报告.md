## 二、执行过程与自修复记录

本轮 **不启用平台自动修复**（`auto_repair=false`），以取得干净基线；所有修正由人工定位后改脚本，
目的是让每条断言都指向真实行为，不因自动修复而被放宽。

先做了一轮 **DOM 侦察**（3 次 runner 执行，覆盖登录页 / 首页 / 12 个管理页），把页面真实列名、
按钮文案、查询占位符抓回来，再用真实字段写需求文档与断言。这避免了一类典型误报：按产品文档
想象中的字段名写断言。

迭代中修掉的**脚本自身问题**（非被测系统缺陷）：

1. **element-plus 的中文按钮会插入空格**：无图标按钮渲染成 `确 定` / `取 消`，
   `getByRole('button', { name: '确定' })` 匹配不上，点击会一直等到用例超时（90s）。
   改为容忍空格的匹配（`/确\s*定/`）。这也解释了首轮两个"挂死"用例。
2. **侧边栏子菜单是异步渲染的**，登录后立即读取菜单会只拿到一级项。改为登录后等待渲染完成。
3. **`el-select` 的 placeholder 输入框被包裹层遮挡**，直接点它会无限等待；改为点击
   `.el-select` 容器。后续为降低脆弱性，把"写入类"用例从带富文本编辑器的公告弹窗
   换成纯文本框的参数配置表单。
4. **`CRON 表达式`等表头本身没问题**，首轮失败是因为工具条按钮选择器用了 `.el-main button`
   （该页面实际不匹配），改为全局 button 文本集合。
5. **`:visible` 伪类在本环境的 el-dialog 上表现不稳定**，一律改用 Playwright 的
   `getByRole`（其可访问性树天然排除隐藏元素）。
6. **测试数据本身踩了业务校验**：首轮用 17 字符的错误密码，被后端"密码长度 4-16 位"
   参数校验先拦下，根本没走到密码比对；改成合法长度的错误密码后才真正测到该路径。

随后发现并修复了**平台自身的一个缺陷**（非本轮交付内容，但阻塞了脚本迭代）：
`PUT /api/v2/web-ui-auto/scripts/{id}` 返回 500 —— `updated_at` 带 `onupdate=func.now()`，
UPDATE 后该属性被 SQLAlchemy expire，异步会话里再访问触发同步懒加载（`MissingGreenlet`）。
已在 commit 后补 `await db.refresh(row)`，并同步修复了 `unity_auto.py` / `api_auto.py` 里
同样模式的更新接口。

## 三、发现的缺陷

### 缺陷 1（P1）密码错误时登录页无任何反馈，用户看到的是"点了没反应"

- **涉及需求**：REQ-AUTH-001（"凭据错误 → 停留登录页并给出错误提示"）、EDGE-003
- **现象**：输入正确租户名 + 正确用户名 + 错误密码，点击「登录」后页面**完全没有反馈**——
  无错误提示条、无字段级错误、无跳转，密码框内容保留，用户无法判断是密码错了还是页面卡了。
- **证据链**（三层取证一致）：
  1. 网络：`POST /admin-api/system/auth/login` 返回 `HTTP 200`，
     body `{"code":1002000000,"msg":"登录失败，账号密码不正确","data":null}` —— 后端给了明确文案；
  2. DOM：点击后以 **100ms 粒度轮询 9 秒**，`.el-message` 计数恒为 0，
     `.el-form-item__error` 为空，`.el-notification/.el-alert` 为 0；
  3. 控制台：无 `console.error`、无 `pageerror`，即前端也没有抛错，是**静默吞掉**了业务错误码。
- **补充观察**：后端本身是对的——同一次失败在 `system_login_log` 里留下了 `result=10` 记录。
  问题纯在前端未把非 0 业务码渲染给用户。
- **影响**：这是登录页最基础的错误反馈，任何输错密码的用户都会遇到；容易被误判为系统故障。
- **建议**：检查前端 axios 响应拦截器对 `code !== 0` 的处理，确认登录接口没有被
  `showError: false` 之类的配置豁免；补一条"非 0 业务码必须提示 msg"的回归用例。

### 缺陷 2（P1）操作日志在本范围内完全不产生记录

- **涉及需求**：REQ-LOG-001（"执行一次新增/修改/删除操作后，能在操作日志中查到对应记录"）
- **现象**：在界面上完成一次真实的参数配置**新增 → 删除**（两步都提示成功、数据确实落库与消失），
  随后打开 `系统管理 → 审计日志 → 操作日志` 点击搜索，结果为 **「共 0 条」**。
- **证据链**：
  1. `system_operate_log` 表行数恒为 0（多轮写操作前后均是）；
  2. 后端日志中没有操作日志相关异常，说明不是写入失败被吞，而是**根本没有触发**；
  3. 代码层定位：`yudao-module-system` 的 **35 个控制器**与 `yudao-module-infra` 的
     **16 个控制器，无一使用 `@OperateLog` 注解**（以 `ConfigController.createConfig` 为例，
     方法上只有 `@Operation` 与 `@PreAuthorize`，没有 `@OperateLog`）。
- **结论**：操作日志的**机制**（切面、`OperateLogApi`、菜单与查询接口）都在，
  但这两个模块**未接入注解**，导致功能形同虚设——页面能打开、能查询，永远查不到数据。
- **影响**：后台审计能力缺失。对需要留痕的合规场景（谁改了权限、谁删了用户）无法追溯。
- **建议**：给写操作补齐 `@OperateLog(type = CREATE/UPDATE/DELETE)`；
  或在需求侧把该能力降级为"平台不提供"并从范围中移出，避免后续回归持续红灯。

### 观察项（未判为缺陷，供参考）

- **`infra_api_access_log` / `infra_api_error_log` 恒为空**：原因是 `application-local.yaml` 中
  `yudao.access-log.enable: false`（上游 local profile 默认关闭访问日志）。属上游既定配置，
  且「API 日志」本就在本次范围之外。
- **租户名不存在时的错误语义**：前端在租户名解析不到时不带租户编号发请求，后端返回
  "未传递租户编号"而非"租户不存在"。行为符合需求（拒绝登录），但错误语义对用户不够准确。
- **密码框不拦截超长输入**：17 字符密码会通过前端校验、发出请求，再由后端以
  "密码长度为 4-16 位"拒绝，且该错误同样不展示（与缺陷 1 同源）。前端可加长度校验前置拦截。
- **未处理异常会被伪装成「系统异常」**：向一个不存在的接口路径 POST（带 body）时，
  返回的是 `{"code":500,"msg":"系统异常"}` 而不是 404。原因是错误页转发会把请求再走一遍
  过滤器链，`ApiAccessLogInterceptor.preHandle` 此时二次读取已被消费的请求体，抛
  `IllegalStateException: getInputStream() has already been called for this request`
  并覆盖掉真实异常。任何未被业务异常处理器接住的错误都会因此丢失原始信息，排障时只能靠后端日志。
- **数据源配置没有「测试连接」**：我最初在需求文档里按通用后台的惯例写了"支持测试连接"，
  实测该页面**没有任何查询条件、也没有测试连接按钮**，后端仅有
  `create / update / delete / delete-list / get / list` 六个接口。已修正需求文档 REQ-DS-001，
  并把该项从可测范围中移除。同一轮核实还发现字典数据页、租户套餐页、代码生成的行内操作
  未逐一核实，已在需求文档中逐条标注"待执行时确认"，避免用例写死未经核实的字段名。
