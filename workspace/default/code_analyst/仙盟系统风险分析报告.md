# 仙盟（Union）系统风险分析报告

> 分析范围：`/repo/server/game_server/game/mods/clan/**`（UnionD / UnionUserD / UnionSerialExecuteD / FUnion / ClanOb / clan.gs / ClanD）、`game/mods/gm/daemons/GmUnionD.gs`、`game/protocols/Union.xml`，以及客户端 `client/Assets/Lua/Game/`（Manager/UnionD.lua、Enum/UnionEnum.lua、UI/Module/Union/**、msg_clan_op.lua）。
> 方法：全量阅读服务端仙盟核心代码 + 客户端协议/UI 对照核实，所有结论均标注 `文件:行号` 证据。

---

## 一、系统架构速览

- **仙盟 = 多个宗门(clan)结成的跨服联盟**，代码全部在 `clan` 模块内（`gang` 模块是旧宗门服务，与仙盟无关）。
- **主宗门(master clan)持有权威 `union_dbase`**（members / union_rid / union_name / union_owner / union_star / union_combat_capacity 等），成员宗门持全量副本，经 RPC + `UnionSerialExecuteD` 串行队列同步（UnionD.gs:1891-1940）。
- 宗门服务运行在**单协程域**（"clan.coroutines"，co_count=1），跨协程用 `function.call_in_domain`；但**闭包内的同步跨服 RPC 会让协程挂起**，期间域可被其他请求插入——这是多个竞态问题的根源。
- 协议入口：`Union.xml` 16 条命令 → `UnionUserD`（`#pragma parallel`，UnionUserD.gs:5，玩家域并行，**不在 clan 单协程保护内**）。
- 配置：`gang_union_config / gang_union_power / gang_union_score / gang_union_score_rank`，经 `UnionD.get_config`（UnionD.gs:128-134）读取，**缺失返回 nil、无默认值**。
- 每日 2:30 自检 `union_check_valid`（UnionD.gs:2634-2655）、10:30 检查星级数据（2564-2574）；宗门联赛(gang_season)期间 `is_union_op_ban` 封锁仙盟操作；赛季结束 `dismiss_all_union` 解散全部仙盟并 300s 后强删兜底（2434-2463）。

## 二、风险清单（按严重程度分级）

### 🔴 P0 — 资损类（可直接造成玩家损失）

#### R1. 仙盟改名 RPC 网络级失败不退款
- **位置**：`UnionUserD.gs:786-812`（request_set_union_name）
- **链路**：扣物资 `user.cost_clan_supplies(item_amount, "union_change_name")`（:788）→ 跨服 RPC `rpc_union_change_name`（:795）。
- **问题**：RPC 返回**非数组**（网络级失败/超时，:796-799）时直接 `return {"ok":false,"reason":"union_rpc_error"}`，**已扣的宗门物资不退还**。只有 `rpc_ret[0].ok==false`（业务级失败，:800-812）分支才走 `add_clan_supplies(item_amount, "union_rename_return")` 退款。
- **影响**：主宗门所在服瞬时抖动/重启时，改名玩家宗门物资白扣。属于确定性资损路径。
- **修复建议**：把网络级失败分支并入退款逻辑（与 :803-809 相同处理）。

#### R2. 创建仙盟双击并发 → 双扣费 + 断言崩溃
- **位置**：`UnionUserD.gs:28-45`（request_create_union）、`FUnion.gs:132-136`（new_union_data）
- **链路**：`check_can_create_union`（内部 `call_in_domain` 异步校验 is_union()==false，:83-86）→ 回到玩家域扣费 `cost_clan_supplies`（:36）→ `create_union`（:43）→ `new_union_data`。
- **问题**：
  1. **无幂等锁**。对比 `request_union_list` 有 `is_request_union_list` temp 锁（:101-103），create 路径没有任何请求去重；UnionUserD 是 `#pragma parallel`，双击/连点的两个请求在玩家域并行，两次都通过 clan 域校验、**两次扣物资**。
  2. 第二次 `create_union` → `new_union_data` 首行 `assert(is_union() == false)`（FUnion.gs:134）直接**断言崩溃协程**，而不是优雅失败+退款——双扣的物资永远不会退。
- **影响**：快速双击"创建"按钮的玩家被双扣宗门物资（创建成本 `union_create_cost`），且第二次请求以崩溃收场。
- **修复建议**：加 user temp 原子标志（进 clan 域 set、defer 清理）或 clan 侧幂等键；`new_union_data` 改为返回错误而非 assert。

### 🟠 P1 — 数据一致性 / 跨服状态类

#### R3. 确认结盟邀请：先删本地邀请再验证主宗门，RPC 瞬时失败邀请永久丢失
- **位置**：`UnionUserD.gs:512-559`（request_confirm_invite）
- **链路**：进入 clan 域 → 读 `union_invite_list[union_rid]` → **删除并 save**（:527-530）→ `rpc_check_union_master`（:536）失败时 `union_rpc_error` 返回（:550-554）。
- **问题**：主宗门服瞬时不可达时，本地邀请已被删除且持久化，玩家既没加入仙盟、邀请也没了，只能等对方重新邀请（对方盟的 `invite_clan_list` 仍标记已邀请，见 UnionUserD.gs:457-482，状态互相矛盾：邀请方看"已邀请"、被邀方列表为空）。
- **修复建议**：把本地删除挪到 RPC 成功之后，或失败时回滚重插。

#### R4. 成员服"存活检查"是空壳，防重机制形同虚设
- **位置**：`UnionD.gs:2619-2623`（rpc_check_union_server_alive）、`2587-2616`（rpc_check_union_rpc_alive）
- **问题**：`rpc_check_union_server_alive` 函数体**恒返回 `[true]`**。上层 `rpc_check_union_rpc_alive` 遍历仙盟所有成员宗门所在服逐个调用它（:2604-2614），意图是"任一成员服不可达则封锁仙盟操作"，实际**只验证了主宗门服本身 RPC 可达**（RPC 本身能返回就证明主宗门服活着，其余检查全部空转）。
- **影响**：设计上"所有成员服在线才允许操作"的防护（改名/退出/踢人/禅让等全部前置调用 `check_union_rpc_alive`）从未真正生效；成员服离线时执行退出/踢人，副本同步必然半途失败（见 R5），留下脏数据。
- **修复建议**：实现真实探活（或至少 ping 节点状态），否则删掉这个循环减少误导。

#### R5. union_dbase 广播同步失败被吞，副本长期不一致 + 自检无修复
- **位置**：`UnionD.gs:697-716`（broadcast_union_dbase_to_members）、`2663-2680`（master_check_union_valid）
- **问题链**：
  1. 同步失败仅 `catch(assert(false))` + 打日志（:710-714），**不重试不入队补偿**，成员宗门副本停留在旧版本（成员列表/星级/盟主与主宗门不一致）。
  2. 每日 2:30 自检 `union_check_valid` → `master_check_union_valid` 发现 `not_clan_members`（该宗门已不在主宗门 members 里但本地仍是 union 对象，即"僵尸联盟成员"）时**只打 TRACE_ERROR 返回**（:2674-2677），调用方（:2654）不处理返回值，**无任何自动修复/清理**。
- **影响**：跨服抖动一次，脏副本可能一直存在到赛季解散；僵尸成员宗门会继续参与联赛报名等下游逻辑（GangSeasonUnionD 侧读取）。
- **修复建议**：同步失败进 `UnionSerialExecuteD` 延迟重试；自检发现不一致时下发 union_dismiss 修复。

#### R6. 自动结盟部分失败，留下"半个仙盟"
- **位置**：`UnionD.gs:2286-2420`（auto_make_union / auto_make_union_imp / clan_auto_make_union）
- **问题**：赛季初自动结盟逐盟 RPC 创建（:2332-2345，失败 `continue`）；`clan_auto_make_union` 先 `create_union`（:2403）再逐个 `clan_join_union_imp` 拉人（:2407-2418，失败 `continue`）。中途任何 RPC 失败都会留下"主宗门已建盟、部分成员没进来"的残缺状态。成员宗门被拉入失败后**不会重试**，只能等盟主手动邀请。兜底只有赛季末 300s 强散（:2452-2462），即残缺状态会持续整个赛季。
- **修复建议**：join 失败的宗门记录重试队列，或把整个 auto_make 设计为主宗门服单点串行执行。

#### R7. 宗门退出仙盟：闭包失败路径元组长度不匹配
- **位置**：`UnionUserD.gs:657-663`（request_exit_union_clan）
- **问题**：外部按 **7 个变量**解构 `let array rids, int member_count, string union_rid, string union_name, bool is_master_clan, object clan_ob, int union_star = function.call_in_domain(...)`；但闭包内 `clan_ob == nil` 分支 `return [nil, false, nil]` 只有 **3 个元素**。该路径下 `union_name/union_star` 等变量取值未定义，后续发邮件（:687-697，`send_content_mail(mail_id, user_rid, [union_name])`）与日志（:698-700）可能空引用报错，退盟流程中断。
- **修复建议**：失败分支补齐 7 元素，或改用 map 返回。

### 🟠 P1 — 并发竞态类

#### R8. 副盟主任免数量超限竞态
- **位置**：`UnionUserD.gs:990-1025`（request_appoint_union_vice_owner）
- **链路**：clan 域闭包内：读 `cur_count = union_data.union_vice_owner_num`（:1001）→ 校验 `cur_count >= get_config("max_vice_leader")`（:1002）→ **跨服 RPC** `rpc_set_union_vice_owner`（:1010，等待期间 clan 域协程挂起）→ 回来后 `set_vice_owner_count(cur_count + 1)`（:1023）。
- **问题**：盟主快速对**两个不同宗门**的成员各点一次"任命副盟主"：请求 A 在 RPC 挂起期间，请求 B 进入闭包读到的还是旧 `cur_count`，两者都通过校验 → 实际副盟主数**超过 max_vice_leader**。数量字段最终被两次 `cur_count+1` 写成同一个值，计数也与实际不符（少计）。
- **佐证**：系统另有事后矫正 `refresh_union_vice_owner_num`（UnionD.gs:1334-1343，逐盟 RPC 重数），但只在踢人/主宗门变更时触发（:1161-1163、FUnion.gs:205-207），任免路径本身依赖增量计数。
- **修复建议**：RPC 成功后重新读当前值再 +1（或在 RPC 前先占位预扣计数，失败回滚）。

#### R9. 仙盟重名跨服 TOCTOU + 重启丢名册
- **位置**：`UnionD.gs:273-289`（is_exist_union_name，逐服串行 RPC）、`319-336`（register/unregister_union_name）
- **问题**：
  1. 校验（is_valid_union_name → is_exist_union_name）与注册（create_union → register_union_name，:444）之间存在跨服竞态窗口，匹配组内两服同时创建同名仙盟可双双通过。
  2. 名册 `union_name_dict` 存 **query_temp（内存）**（:301、:314-316），依赖 `set_local_local_names` 跨服同步；未观察到服务器重启后本服名字集合的恢复逻辑——重启初期本服重名检查可能漏判（不确定项，建议进一步查 load/启动流程）。
- **影响**：低概率同名仙盟并存，后续改名/解散时的 unregister 按 name 删除会误删对方条目。

#### R10. 申请加入仙盟无数量上限（请求放大向量）
- **位置**：`UnionUserD.gs:165-200`（request_apply_union）
- **问题**：一个宗门可向匹配组内**任意多个**仙盟连续发申请，每次申请 = 主宗门服 RPC + 写入对方 `union_apply_list`（存于 union_dbase 并随全量副本同步广播）。无冷却、无在途申请上限。恶意/脚本客户端可刷跨服 RPC 并撑大各盟 dbase（申请列表随 broadcast_union_dbase 全量同步）。
- **修复建议**：限制在途申请数（如同时最多 N 个），或统一冷却。

### 🟡 P2 — 崩溃 / 健壮性类

#### R11. get_config 无默认值直接参与运算/比较（配置缺失即崩协程）
- **位置**（`get_config` 缺 key 返回 nil，UnionD.gs:128-134）：
  - `UnionD.get_config("union_change_name_cooldown") * HOUR_TIME` — UnionUserD.gs:761（nil×int 运算错误）
  - `time.time() - last_change_info_time < cold_time`（cold_time=nil）— UnionUserD.gs:861-864
  - `union_change_info_times >= get_config("union_announce_mail_max_time")` — UnionUserD.gs:870
  - `cur_count >= get_config("max_vice_leader")` — UnionUserD.gs:1002
  - `cur_count >= UnionD.get_config("member_add_limit")` — ClanOb.gs:521（影响**所有宗门加人**热路径）
  - `len > get_config("union_announce_max_words")`（nil）— UnionD.gs:397-400
  - `union_max_star` 参与比较/加法 — UnionD.gs:814、970、2288；FUnion.gs:288
- **影响**：`gang_union_config.xlsx` 漏配任一行，对应功能协程直接报错中断（加人、改名、公告、任免等），且报错信息晦涩。多数调用点没有 `?? 默认值` 兜底（对比 :355 `get_config("max_name_len") ?? 4` 是正确写法）。
- **修复建议**：统一封装 `get_config(key, default)` 或启动时校验必填配置齐全。

#### R12. clan.gs get_clan_level_point 不判空
- **位置**：`clan.gs:749-762`
- **问题**：遍历 `rid_list` 直接 `this.get_clan(clan_rid).query("level")`，`get_clan` 对不存在的 rid 返回 nil 时**空引用崩溃**。传入了脏/过期 rid（合服、宗门刚解散）即崩。
- **修复建议**：循环内判 `!clan_ob continue`。

#### R13. GM 工具空引用（低危，GM 专用）
- **位置**：`GmUnionD.gs:242-249`（rpc_set_clan_limit）
- **问题**：`get_obj_var(UnionD, "_config").deep_dup()` 后直接 `data.member_add_limit.value = limit`，若配置缺 `member_add_limit` 行则 nil.value 崩 GM 协程。

#### R14. replace_union_data 新盟主数据缺失时仅打日志
- **位置**：`FUnion.gs:187-213`
- **问题**：主宗门退出、盟主迁移到本宗门时，若 `members[new_owner]` 缺失（新盟主已退宗等异常时序），只 TRACE_ERROR 跳过设置 OWNER 职位（:191-195），union_dbase 已替换、职位却没人持有 OWNER——联盟进入"无主"状态，后续改名/任免/解散全部被权限拦截。
- **修复建议**：缺失时应回退迁移或触发重选。

### 🟡 P2 — 性能类

#### R15. get_clan_ob_by_union_rid 全量线性扫描，热路径 17 处调用
- **位置**：`UnionD.gs:227-239`（遍历 `clan.get_clans()` 逐个过滤）
- **调用面**：apply/check_master/踢人/改名/公告/存活检查/自检/成员同步等 17 处（:583、623、684、992、1016、1046、1085、1438、1463、1574、1596、1748、1923、2591、2667…），其中含跨服 RPC 入口与每日自检全量遍历。宗门数量大的服上每次 O(N)，无 union_rid→clan_rid 索引缓存。
- **修复建议**：维护 `union_rid → clan_ob` 字典（创建/解散/迁移时维护）。

#### R16. calc_clan_star O(宗门成员数 × 榜单大小) 嵌套循环
- **位置**：`FUnion.gs:503-525`
- **问题**：对每个"未入榜但战力超门槛"的成员，内层再全表扫描 `rank_list`（跨服合并战力榜，最大 `get_max_range_rank()` 条）逐条比较。全员大盟 + 榜单 2000 条时为百万次比较，且在 clan 单协程域内执行（calc_all_clan_star，UnionD.gs:1789-1798），**阻塞整个宗门/仙盟操作**。`gm_calc_clan_stars`（GmUnionD）同构。
- **修复建议**：把 rank_list 预排序为 (combat_capacity, rank) 数组后二分。

#### R17. 星级刷新依赖"首服"执行，单点脆弱
- **位置**：`UnionD.gs:1759-1777`（refresh_all_clan_star，仅 `server_ids[0]` 生成并广播）
- **问题**：匹配组第一服当天不在线（或合服后 get_match_servers 顺序变化导致"首服"漂移），当日星级不刷新；次日 10:30 的检查（2564-2574）也只打一行 ERROR 不补救。
- **修复建议**：改为"首服优先、其余服检测未收到则接管生成"的互斥模式。

#### R18. UnionSerialExecuteD 队列容量与赛季末风暴
- **位置**：`UnionSerialExecuteD.gs:15-16`（TASK_TIMEOUT_MS=3000、warn_size=1000、pending_size=2000）
- **问题**：所有成员数据同步（sync_clan_member_data / on_sync_clan_member_data，UnionD.gs:1891-1940）排队串行；赛季结束 `dismiss_all_union`（全盟逐宗门 RPC + 邮件 + 广播）会在同窗口打入大量任务，跨服抖动时任务超时（>3s 报警）与积压（>1000 告警）叠加，解散拖长且占内存。
- **备注**：单协程串行本身是正确性设计，风险在容量与风暴叠加时的雪崩。

#### R19. 重名检查逐服串行 RPC
- **位置**：`UnionD.gs:273-289`
- **问题**：`is_exist_union_name` 对匹配组逐服串行 RPC；被创建/改名/自动结盟（clan_auto_make_union :2388-2399 循环内调用）路径复用，匹配组大时创建耗时线性放大（且在 clan 域闭包内挂起，放大 R8 类竞态窗口）。

### 🟢 P3 — 设计 / 前后端一致性类

#### R20. 客户端公告"每日群邮上限"读错字段（确认 bug，影响 UI）
- **位置**：客户端 `UnionD.lua:229-236`（is_announce_mail_daily_max 读 `union.mass_email_daily_use`）
- **事实链**：
  - `mass_email_daily_use` 是**宗门公告**的每日计数字段（服务端 ClanD.gs:2121-2135 写入、ClanImpD.gs:55 SYNC 字段、客户端宗门公告窗口 ChangeAnnouncementWindow.lua:138 也读它）；
  - 仙盟公告每日次数实际字段是 `union_dbase.union_change_info_times`（服务端 UnionD.gs:1471-1472 累加、FUnion.gs:476-487 每日重置）；
  - 仙盟 union_dbase（客户端 `_current_union`）里**根本没有** `mass_email_daily_use` 键。
- **影响**：`daily_use` 恒为 0，仙盟公告窗口（UnionAnnouncementWindow.lua:133）的"今日已达上限"提示**永远不会出现**（服务端限制仍生效，broadcast 会被静默降级为不群邮，UnionUserD.gs:859-872），玩家视角表现为"点了群邮但没人收到邮件且无任何提示"。
- **修复建议**：客户端改读 `union_change_info_times` 并与 `union_announce_mail_max_time` 比较。

#### R21. union_dbase 初始字段 `union_info` 是死字段
- **位置**：服务端创建时初始化 `"union_info": ""`（UnionD.gs:435），但改公告实际写 `"info"` 键（UnionD.gs:1466）。客户端枚举明确 `INFO="info"` 为展示真源、`UNION_INFO="union_info"` 标注为"兼容/冗余"（UnionEnum.lua:91-92），无读取方。
- **影响**：无功能故障，但两键并存易诱导后续开发读错键；建议初始化统一为 `info`。

#### R22. 杂项
- `request_set_union_info` 冷却/上限判定读的是**调用方本地副本** union_dbase（UnionUserD.gs:850-875），非主宗门侧权威数据，副本滞后时可绕过冷却（服务端主宗门 `union_change_info` 累加计数 :1471-1473 为准，但 broadcast 降级判断在发起方，轻微）。
- `union_broadcast_self_text`（UnionD.gs:2684-2700）与 `get_clan_ob_by_union_rid` 一样内联线性扫描，未复用。
- 邮件通知链中 `mail_id` 取自配置（如 :2507 `disband_union_mail`），配置缺失时 `send_content_mail(nil, ...)` 行为依赖 MailD 容错（未核实，建议补默认值）。
