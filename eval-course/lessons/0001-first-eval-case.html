智能体测评 · 第 1 课

写一条用例，跑出分数，让门禁替你下结论

这节课你把整条闭环亲手走一遍：写一个评测集 → 起一个批次 → 读懂每个分数 → 看 trace → 让门禁给出判决。做完你会有一个能反复重跑的「回归入口」。

预计 25 分钟（其中 5 分钟在等智能体跑）· 前置：能打开 http://localhost:5013/eval · 环境是干净的（bash tools/reset-data.sh 可随时回到空场）

先看清整条链路：谁负责什么

评测集是代码，分数是观测，门禁是判决。

  1. 写评测集
    YAML：任务 + 期望
  2. 起批次
    平台驱动智能体
  3. 打分
    确定性 + LLM 裁判
  4. 上报
    trace 与分数进 Langfuse

后面两步在你按下「启动」之后自动发生：每条用例跑完立刻落库（所以页面上是一条一条长出来的），整批结束后汇总均分、求值门禁、写回批次结论。

关键区分：「分数」和「判决」是两件事。分数来自打分器，判决来自门禁表达式。门禁留空时，只要没有执行异常，批次就是 passed——哪怕分数很难看。这一点第 4 节会再讲一次。

用例设计：三个字段决定一切

一个评测集文件（datasets/*.yaml）由若干 item 组成，每个 item 就三块内容。你写什么，决定了后面能拿到哪些分数。

字段写什么不写会怎样
input交给智能体的任务原话。要写成可判定的产出要求：几条、什么格式、什么语言。没有输入就没得跑
expected机器能验的期望：contains / not_contains / tools / max_tool_errors / evidence这几项对应的分数不会产出（不是 0 分，是没有这一项）
judge需要读懂语义才判得了的标准：criteria + 及格线 pass没有 LLM 裁判分数

设计要点（写第一条时最容易踩的）

  • input 里把"几条、什么格式"写死，否则 judge 的"恰好 3 条"无从判断——判据必须在任务里交代过，这叫可判定性。
  • 能自动判的不要写进 judge：包含某个词、必须调用某个工具、报错不超过几次，这些都是确定性的，交给 expected；judge 只用来判"内容对不对、有没有真核实过"。
  • judge 的 criteria 要写成"判不通过的条件"（"多于或少于 3 条判不通过"），比只写正面要求更能压住模型的宽容倾向。

动手：把你的第一条用例跑起来

第 1 步 · 在页面上新建评测集

在 /eval 页面的「评测集」卡片右上角点「新建评测集」，按这张表填（表里左边是界面字段，右边是它写进文件的位置）：

界面字段填什么
文件名my-first.yaml（写进仓库的 datasets/）
评测集名 namemy-first
被测 agenttestcase_agent
用例 · 任务（input）为一个「手机号 + 验证码」登录功能列出 3 条最关键的测试点。
每条一行，用「1. …」这样的编号列出，只写测试点，不写用例细节。
确定性期望 · 答复须包含验证码
LLM 裁判 · 评审标准回答必须恰好 3 条、编号成列，且三条都与手机号 + 验证码登录相关（例如验证码错误、验证码过期、手机号格式非法）。多于或少于 3 条判不通过。
LLM 裁判 · 及格线0.7

点「创建」。保存的不是数据库里的一行配置，而是真的写了一个 YAML 文件——点开列表里的「编辑」，展开「查看磁盘上的原始 YAML」，你会看到它长什么样（多行任务落成 | 块，中文不转义）。文件是唯一事实源：直接手改也行，页面每次打开都从磁盘读回。

为什么用 testcase_agent：它的输入输出都是纯文本，没有外部依赖，跑一条约 10 秒——适合把机制看清，而不是把时间花在等浏览器上。

第 2 步 · 起批次

  1. 在 /eval 点右上角「启动测评」。
  2. 评测集选 my-first.yaml（刚建的集子立刻出现在下拉里，不用重启任何东西）。被测 agent 会自动填成 testcase_agent。
  3. 门禁表达式填：avg(llm_judge)>=0.6 && all(task_output_match)（含义：所有用例的「答复命中期望片段」都为真，且 judge 平均分不低于 0.6）。
  4. 点「启动」，然后打开这条批次的「详情」。

第 3 步 · 盯着实时面板看

你会在详情里看到：正在跑：login-001 mm:ss、「agent 在做什么（实时）」里逐条冒出 模型生成中 · 某模型、以及「执行日志（实时尾部）」。这一栏是执行进程边跑边写的现场（workspace/default/eval-runs/<批次id>/），不是猜的进度。

第 4 步 · 读分数

跑完（约 10–30 秒）用例表会有一行 login-001。这份评测集只会产出 3 个分数，逐个看：

分数名谁算的怎么算怎么读
task_output_match确定性打分器最终答复里是否出现 contains 里的任一片段布尔值。它是"事实核对"，最便宜也最可信
llm_judgeLLM 裁判裁判模型按 criteria 打 0–1 分，理由写在分数的 comment 里数值。看分数一定要同时看 comment（理由）
llm_judge_passLLM 裁判llm_judge 是否 ≥ 数据集里的 pass布尔值。门禁里用它比用原始分更稳

没写 expected.tools 就没有 tool_sequence，没写 max_tool_errors 就没有 tool_errors——分数是"按需产出"的，别把"没有这个分数"误读成"这项是 0 分"。

第 5 步 · 去 Langfuse 里看这条运行的轨迹

用例行的「链路」列有一个 trace 链接，点开是 http://localhost:3000/project/<项目id>/traces/<traceId>。在那里你能看到：输入（你的 input）、每一次模型调用（模型名、耗时、token）、以及最终输出。分数就挂在这条 trace 上——分数与轨迹是同一个对象，这是这套测评能被信任的原因。

读懂判决：passed / failed / error

批次状态含义
passed门禁通过 且 没有任何用例执行异常
failed有用例执行异常（但没全挂），或门禁没通过
error所有用例都执行异常（通常是环境问题：agent 名写错、模型端点不通）

「执行异常」只看用例有没有跑起来，与分数高低无关。

实测过的一次真业务批次：6 条用例全部跑通、状态 passed，但均分只有 0.667（两条没产出期望内容）。如果门禁留空，这种"看起来通过、实际不达标"的批次会被当成绿灯——所以回归一定要写门禁。

门禁为什么"写错字也算失败"？（fail-closed）

门禁里写了没人产出的分数名（比如把 llm_judge 写成 llm_judeg），求值时会直接判失败，而不是当作"没有约束"。理由是：一个打错字的门禁读成"全过"，比读成"失败"危险得多——前者会把坏版本放进线上。

改一次，再跑一次（这一步别跳过）

把 input 里的「3 条」改成「5 条」，其它都不动，再起一个批次。你会看到 llm_judge 掉下去、comment 里出现"多于 3 条"之类的理由——因为 judge 的判据里写死了 3 条。

这个动作的意义：你刚刚用一次可复现的实验证明了"用例的判据与任务描述必须一致"。这就是测评的全部手感——改一处、跑一次、看分数怎么动。做完了记得把文件改回去。
