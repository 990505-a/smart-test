2. Create `src/app/api/v2/messages.py` with:
   - `GET /threads/{thread_id}/messages` endpoint accepting `limit` (default 20, max 100) and `cursor` (message ID, optional)
   - Use `langgraph_sdk` Python client (already installed via DeepAgents) to call `client.threads.get_state(thread_id)` server-side
   - Use `settings.langgraph_api_url` from config.py for the client URL
   - Implement **conversation group slicing**: when slicing at a boundary, scan backwards from the cut point to include any tool messages that belong to the last AI message in the page. A tool message belongs to an AI message if it appears sequentially after the AI message and has `tool_call_id` matching one of the AI message's `tool_calls[].id` or `additional_kwargs.tool_calls[].id`. Never split an AI message from its tool results.
   - Return JSON: `{ messages: [...], total: number, has_more: boolean, next_cursor: string|null }`
   - `next_cursor` is the ID of the FIRST message in the returned slice (used to fetch messages before it)
   - Cursor-based pagination: if `cursor` provided, find the message with that ID, then return messages BEFORE it (older messages). If no cursor, return the LAST `limit` messages (most recent).
   - `serialize_message()` helper: handle both dict-style and object-style LangGraph messages. Include `id`, `type`, `content`, `additional_kwargs`, `tool_calls`, `name` fields.
   - Error handling: return 404 for unknown threads, 400 for invalid cursor
   - Use `from langgraph_sdk import get_client` (sync import pattern matching project convention for LangGraph client)

3. Register the router in `src/app/api/__init__.py`:
   - Import `messages` from `src.app.api.v2`
   - Add `api_router.include_router(messages.router, tags=["Messages"])`

NOTE: The `get_client` function from langgraph_sdk creates a sync client. For async FastAPI, use `from langgraph_sdk import get_async_client` instead, which returns an `AsyncClient` with the same API but async methods. If `get_async_client` is not available, use `from langgraph_sdk import Client` and call in a thread via `asyncio.to_thread`.

  <files>webui/src/lib/api/messages.ts, webui/src/app/types/types.ts, webui/package.json</files>
  <action>
1. Add types to `webui/src/app/types/types.ts`:
   ```typescript
   /** Message shape returned by the paginated backend endpoint. */
   export interface PaginatedMessage {
     id: string;
     type: "human" | "ai" | "system" | "tool";
     content: string | Array<Record<string, unknown>>;
     additional_kwargs?: Record<string, unknown>;
     tool_calls?: Array<{ name: string; args?: Record<string, unknown>; id?: string }>;
     name?: string;
   }

   /** Response shape from GET /api/v2/threads/{threadId}/messages */
   export interface PaginatedMessagesResponse {
     messages: PaginatedMessage[];
     total: number;
     has_more: boolean;
     next_cursor: string | null;
   }
   ```

2. Create `webui/src/lib/api/messages.ts`:
   - Use existing project pattern from `useProjects.ts`: `const API_BASE = process.env.NEXT_PUBLIC_API_URL || "http://localhost:8000"`
   - Use `useSWRInfinite` from `swr/infinite` (swr 2.4.1 is already installed)
   - `getKey(pageIndex, previousPageData)` function:
     - Return `null` if `threadId` is null (no thread selected)
     - Return `null` if `previousPageData` exists and `has_more` is false (no more pages)
     - First page (no cursor): `${API_BASE}/api/v2/threads/${threadId}/messages?limit=${pageSize}`
     - Subsequent pages: `${API_BASE}/api/v2/threads/${threadId}/messages?limit=${pageSize}&cursor=${previousPageData.next_cursor}`
   - SWR config: `{ revalidateFirstPage: false, revalidateOnFocus: false, revalidateOnReconnect: false }`
   - Export `usePaginatedMessages(threadId, pageSize=20)` returning:
     - `messages`: flattened array of all loaded messages (reversed to chronological order -- API returns newest-first pages, but each page is oldest-first within itself)
     - `total`: total message count from first page response
     - `hasMore`: whether more older messages exist
     - `loadMore()`: `setSize(size + 1)` to load next page
     - `isLoading`: initial loading state
     - `isValidating`: background revalidation state
     - `mutate`: SWR mutate for cache invalidation
   - Handle the page ordering carefully: API returns pages from newest to oldest when scrolling up. Each page contains messages in chronological order within itself. When flattening, pages come in order [page0=newest, page1=older, ...]. For display, we want oldest-first, so flatten all pages and reverse.
   - Actually, simpler approach: the API endpoint (per Task 1 design) returns the LAST `limit` messages for the first call (no cursor), and messages BEFORE the cursor for subsequent calls. Each page's messages are in chronological order. Flattening `data.flatMap(p => p.messages)` gives newest-page-first, so reverse to get chronological.
